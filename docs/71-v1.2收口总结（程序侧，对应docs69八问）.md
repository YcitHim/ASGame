## §二 幕事件池挂法核查（「最后一处」，已闭环）

### 2.1 挂载位置：act JSON 的 `layers[].events`（层字段，不是幕级字段）

```json
{
  "id": "l1",
  "width": 3,
  "kinds": ["battle", "altar", "event"],
  "events": ["forge_baptism", "slag_merchant", "…"]
}
```

- 数组元素为事件 id，指向 `src/data/events/*.json`；schema 校验 `z.array(id).min(1).optional()`（`tools/content-validator/src/schema.ts:464`）。
- act 根上**没有** `events` 字段——只有层模板上有。

### 2.2 层继承：`inheritedPool`（`core/map/index.ts:332 / :438 / :253`）

某层不写 `events` → 从该层**向前找最近一个声明了 `events` 的层**整份继承。所以 act1 / act2 只在 **l1 和 l5** 各写一份（同幕同池），其余层自动继承。生成节点时只有 `kind:"event"` 的节点才带池（`makeNode`），随机路径与兜底图两条路行为一致。

### 2.3 抽取：`rollEvent`（`core/map/index.ts:922`）三级回落 + 同幕不放回

1. `node.event` 写死单个（现役 act 未用）＞
2. `node.events` 池 ＞
3. **全事件池兜底**（`content.events.keys()` 排序）——act3 现在就停在这级。

附带规则：**同幕不放回**（docs/54 E7：`seenEvents` 按层记录、抽过剔出、池尽重置回全池）；同种子同事件（`seed ^ layerIndex` 独立 map RNG 流）；本层已抽过原样返回。

### 2.4 validator 门禁（`tools/content-validator/src/validate-content.ts:496-508`，docs/54 §六）

事件池**去重后**：第一幕 ≥8、其余幕 ≥6，不达标报错；**但整幕不写（池为空）不报错**——act3 目前正是靠这条合法回落全池，这正是裁决要消灭的状态（八轴 ⑤「三幕只讲锻炉的故事」会被一二幕事件戳破）。

### 2.5 结论

**docs/70 §3.4 的挂法与引擎实测完全一致**：act3.json 的 l1 与 l5 各加 6 个 id 的 `events` 数组即可，`inheritedPool` 自动惠及全部中段层，**零引擎改动**。

现状池容：act1 = 10 件 · act2 = 9 件 · act3 = 未挂（全池 22 件）。

## §三 特性文案核对结果（docs/70 §二.7 交办：写错就改）

### 3.1 铁皮王八：三处落后

现状文案（`zh-CN.json:960`）：「充能不再加伤，改为每次获得格挡时 +充能层数。回合结束时按本回合格挡判定，每 **8** 点折算 1 层荆棘……荆棘上限提升到 **10** 层。」

| # | 问题 | 实装真值 |
|---|---|---|
| 1 | 「每 8 点折算 1 层」未随 N2 更新 | 每 **10** 点（`bramblePerBlock: 10`） |
| 2 | 「上限提升到 10 层」未随 N1 更新 | 上限 **7**（`brambleMaxStacks: 7`） |
| 3 | 开头「充能**不再加伤**」与 T1 直接矛盾；T1 混合充能整段缺失 | 攻击牌额外获得 **⌊充能÷2⌋** 点伤害（`hybridChargeDivisor: 2`，充能仍全量注格挡——「另分」不是「挪走」，docs/70 §二.7 口径） |

### 3.2 玻璃大炮：三处落后（同一交办口径，顺手核查）

现状文案（`zh-CN.json:962`）：「……每层让你回合开始失去 **2** 点生命……每回合第一张攻击牌附加等同于当前充能的伤害、随后充能清零……」

| # | 问题 | 实装真值 |
|---|---|---|
